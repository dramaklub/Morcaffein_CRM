2. MANAGER DASHBOARD — CRM_Morcaffein/Views/Controls/ManagerDashboardView.cs
=====================================================================

Current layout, top to bottom (FlowLayoutPanel, TopDown — fixed tonight, was a
TableLayoutPanel with a real row-ordering bug before):

  1. Date range filter (Today / 7 Days / 1 Month / Custom) — ABOVE the KPI row.
  2. KPI pods (4, equal width): Total Revenue, Sales per Order, Promos Redeemed,
     Customer Happiness. Each opens a drill-down modal on click.
  3. Peak Hours heatmap (full width) — self-painted grid, PeakHoursHeatmapControl.
  4. Age Demographics (donut, AgeDemographicsControl) + Loyalty Tier Progression
     (grouped column chart, LoyaltyTierProgressionControl) — side by side, 50/50.
  5. Campaign Lift (ActiveCampaignLiftControl) — full width, two-line dual-axis.

  No in-view header — removed tonight as redundant with FrmMain's own top-bar tab
  label ("/ Dashboard").

  KPI pod → modal mapping:
    Total Revenue      -> RevenueDetailModal          (uses PosDiagnosticsDto)
    Sales per Order    -> SalesPerOrderDetailModal     (uses recent orders + AOV)
    Promos Redeemed    -> PromosRedeemedDetailModal    (uses CampaignRoiDto)
    Customer Happiness -> CustomerHappinessDetailModal (uses FeedbackRatingDistributionDto)

  Deliberately NOT shown as standalone chart cards (explicit user decision this
  session): Barista Sales Performance, POS Diagnostics. Their underlying DTOs
  (PosDiagnosticsDto, and BaristaSalesPerformanceDto is fetched nowhere on this
  view at all) still get used where the KPI pods/modals need them — see the
  BaristaSalesPerformanceControl / PosDiagnosticsControl note in section 4.

  Fixes applied tonight (all verified via isolated `dotnet build`, 0 errors — see
  note in section 5 about why a full in-place build kept failing):
    - Root layout bug: TableLayoutPanel had 6 declared rows but no RowStyles ever
      added, combined with every "row" being its own Dock=Top panel — this is what
      was rendering the date filter above the KPI row instead of below it. Fixed
      by switching to a plain FlowLayoutPanel(TopDown) — stacks in insertion order,
      no row-styling ambiguity possible.
    - Removed Campaign Lift by mistake in the same pass that removed Barista Sales
      /POS Diagnostics (user did NOT want Campaign Lift gone — it's a core shared
      chart, not a Manager-only one). Re-added as its own full-width row.
    - KPI row felt cramped: height 84->96px, gap below it 10->18px, gap above (under
      the filter) increased too.
    - Chart rows expanded vertically (Peak Hours 245->280, Age/Loyalty row 255->300,
      Campaign Lift new row at 280) so charts fill their cards instead of leaving
      dead space.
    - Loyalty Tier Progression was rendering ONE stacked bar per month (tiers piled
      on each other) instead of 3 separate bars — ChartType StackedColumn -> Column
      (WinForms Chart auto-clusters same-type Column series side by side).
    - Real bug underneath that: `months = Math.Max(1, days / 30)` in ReloadAsync
      evaluated to exactly 1 for EVERY date-filter preset (Today, 7 Days, 1 Month
      all resolve to months=1 via integer division) — so only one month of tier
      data was ever fetched, regardless of filter selection. Fixed by decoupling
      Loyalty Tier Progression from the KPI date filter entirely — it's a
      trend-over-time chart, it always requests a fixed 6-month trailing window now.
    - Peak Hours heatmap wasn't reflecting new transactions where expected — root
      cause was NOT a refresh/caching bug (verified: fresh instance created per
      nav click, no caching anywhere in the client or API). Actual cause:
      Order.OrderDate is stored in UTC with no local-time conversion, so a sale
      landed in a UTC-shifted hour/day cell, not the one being checked. Fixed in
      the API (`GetPeakHours`) with a fixed PH UTC+8 offset applied before
      grouping — flagged as a hardcoded assumption, would need to become a
      per-tenant setting if this app ever serves shops outside PH.
    - Campaign Lift was a Column+Line combo chart (revenue bars + redemption
      line, dual Y-axis) that visually "looked bad" — diagnosed as Column and Line
      series not reliably agreeing on per-category spacing in this charting
      library, a known-fragile combo. Converted to two Line series (same dual-axis
      setup) per user's own suggestion — removes the spacing-mismatch class of bug
      entirely since both series now share identical alignment logic.
    - CSAT modal (CustomerHappinessDetailModal — used by BOTH dashboards) was
      rendering all 5 star ratings as what looked like one merged bar. Real bug:
      `Minimum`/`IsStartedFromZero` were set on `AxisX`, but for a `SeriesChartType.
      Bar` (horizontal) chart, AxisX is STILL the category axis (role doesn't swap
      between Bar and Column) — forcing numeric-axis properties onto a category
      axis is what scrambled it. Fixed by switching to vertical Column (consistent
      with every other chart in the dashboard) and moving those properties to
      AxisY where they belong. The underlying data was never the problem — the API
      already always returns all 5 star ratings, including zero-count ones.
