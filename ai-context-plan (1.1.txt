====================================================================
1. WHAT THIS PROJECT IS
====================================================================
A Coffee Shop Loyalty & Retention CRM ("Morcaffein") — a WinForms desktop app (.NET,
net10.0-windows) for the STAFF side of the business (baristas/managers at the counter),
backed by a real EF Core + SQL Server database (not just mocked long-term, though the UI
is currently wired to an in-memory mock service layer — see section 4).

The Staff UI has three pillars — ALL THREE ARE UI-COMPLETE against mock data:
  1. Transactions / POS — recording sales           -> DONE
  2. Customer management — search/register/history  -> DONE
  3. Feedback — logging + reviewing tickets         -> DONE (staff side only, see section 3)

Login/auth is explicitly OUT OF SCOPE for now. FrmLogin exists as a stub but is never
shown — Program.cs launches straight into FrmMain, and a placeholder employee session is
seeded in code (see section 4).

The project owner's next-step framing: connect everything to the real database, starting
with one service at a time. See section 8.

2. ARCHITECTURE / STACK DECISIONS
====================================================================
- WinForms, not WPF.
- Hand-rolled MVVM: no MVVM toolkit package. ObservableObject (INotifyPropertyChanged +
  SetProperty) and RelayCommand/RelayCommand<T> (ICommand) are small hand-written classes
  in Common/. Forms wire up ViewModels manually via code-behind event handlers — no
  Control.DataBindings, no XAML-style binding syntax.
- DDD-ish domain entities (CRM_Morcaffein.domain/entities): mostly private-set properties,
  mutated only through domain methods. Campaign is the one entity that still uses plain
  public get/set (not yet refactored).
- EF Core 10 with TenantCrmDbContext (IdentityDbContext-based), SQL Server provider. The
  connection string in CRM_Morcaffein.api/appsettings.json points to a REAL hosted SQL
  Server (db67068.public.databaseasp.net), not localhost. Migrations get generated/applied
  using CRM_Morcaffein.api as --startup-project.
- The DB is a MULTITENANT setup: one master DB tracks tenants, and the currently-connected
  tenant is "tenant A".
- "Card" table layout convention: every management tab (Customers, Feedback) uses the same
  boxed-table pattern — an outer padded panel, a white bordered card containing a header
  row (search box top-left, primary action button top-right) and the DataGridView below
  it. Transactions/POS deliberately breaks from this in its middle/right content since it's
  a different interaction model (a register, not a record browser), but still lives inside
  the same outer card convention for visual consistency.
- Left-side drawer convention: clicking a grid row opens a detail drawer on the LEFT of the
  card showing profile/ticket info. (Transactions/POS uses a left COLUMN for customer
  search instead of a drawer.)
- The outer card's `FixedSingle` border was REMOVED from Transactions this session — it
  doubled up with the Order box's own border on the right edge and read as a thick black
  seam. The Order/Payables/Log Sale boxes keep their own borders and the right column's
  padding insets them from the card edge.

3. KEY BUSINESS RULES
====================================================================
- POINT ADJUSTMENTS ARE A TWO-STEP APPROVAL WORKFLOW, NOT AN INSTANT EDIT:
    * A Manager (Employee.IsManager: Manager/Admin/SuperAdmin) can REQUEST a point
      adjustment for a customer (PointAdjustmentRequest, status "Pending"). Requests
      accept NEGATIVE amounts (deductions) as well as positive — the amount field is a
      NumericUpDown with a negative Minimum, and the domain handles the negative case.
    * Only an Admin (Employee.IsAdmin: Admin/SuperAdmin) can APPROVE or REJECT it.
      Approving actually applies the point change (via Customer.AdjustPoints) and writes
      a PointLedger row; rejecting just closes out the request with no balance change.
    * An employee can NEVER approve their own request.
    * This Staff/Manager app is explicitly NOT the admin console — the approve/reject UI
      exists in code but the placeholder session is seeded as Manager, so in THIS app
      you'll only ever see the "submit a request" half. Admin approval is a different,
      not-yet-built surface.
    * The customer's adjustment-requests list only shows PENDING requests.
- FEEDBACK — THIS APP IS LOG + VIEW ONLY:
    * Any staff member can log a feedback ticket against a customer.
    * The staff console does NOT resolve, dismiss, or award bonus points. Those are a
      MANAGER decision on how to address the feedback (reward or not) and belong on a
      future manager/admin surface. The decision panel that used to live in the Feedback
      drawer has been removed from this app entirely.
    * Staff-side flow: log a ticket → see it in the grid → click a row → see the review
      detail in the drawer (rating, category, status, date, notes). Nothing more.
- TRANSACTIONS/POS ALWAYS requires a real, identified Customer — there is no guest/walk-in
  checkout path in the UI. Picking a customer (via the ID/phone search box) is what starts
  a transaction; before that, the register displays but can't add to cart or check out.
  This is now permanent product policy: the program is designed for customers who are
  already loyalty members or want to register.
- SEARCH-AND-GO STARTS A FRESH TRANSACTION. If a search identifies a different customer
  while a cart has items in it, the app asks for confirmation ("Discard the in-progress
  order for X and start a new one for Y?") before throwing the cart away. Declining
  restores the search box to the currently-loaded customer's ID.
- PROMOS:
    * The promo control is a single BUTTON at the bottom of the left customer column. Its
      label shows the currently-applied promo ("Exam Week ▾") or "Select a Promo ▾". Click
      opens a menu of eligible promos; "Clear applied promo" appears at the top when one
      is active. There is no separate ComboBox — the button is both the state display and
      the action.
    * Applying a promo snapshots a CampaignRedeem row on the Order. Re-selecting the same
      promo is blocked at the UI level (Order.ApplyPromo has no duplicate guard of its
      own — that's a deferred domain fix, see section 7).
    * DISCOUNTS RE-EVALUATE WHEN THE CART CHANGES. Order.RecalculateTotals recomputes
      TotalDiscount by re-running each applied campaign's CalculateDiscount against the
      CURRENT SubTotal, not the snapshot taken at apply time. This is a domain change
      made this session; see section 6.
- Tiers (Regular/Silver/Gold) are labeled as plain text ONLY — no color-coding. Same for
  order/feedback status. The whole palette is brand-brown (#572400) tints/tones/shades
  plus plain white/grey neutrals only (see BrandPalette.cs).
- VAT and PWD/Senior discount on the POS Payables panel are DISPLAY-ONLY placeholders:
  VAT is shown as an informational 12%-of-total breakdown (assumes VAT-inclusive pricing,
  PH-receipt style) and does NOT change what's charged; PWD/Senior Disc. is a static
  ₱0.00 line with no input wired up yet.
- Guest/walk-in orders: the Order entity's constructor requires a positive CustomerId.
  The mock layer has a hidden MockDataStore.WalkInCustomer but the POS UI doesn't
  exercise it. With the "every sale needs a real customer" policy now settled, this is
  no longer a known limitation — it's just dead code that can be removed when the mock
  layer is replaced.

4. WHAT'S MOCKED VS REAL RIGHT NOW
====================================================================
- The domain entities, DbContext, and migrations are REAL and applied to the actual
  remote SQL Server database.
- The UI currently talks ONLY to an in-memory mock service layer (Services/Mock/*, all
  sharing one MockDataStore singleton via ServiceRegistry). This is deliberate — build
  the UI against mocks first, don't touch the real API/HTTPS layer yet. Section 8's
  "connect everything to the database" plan replaces this, one service at a time.
- ServiceRegistry.PlaceholderStaffAccount stands in for "whoever is logged in" until
  FrmLogin/real auth exists. Seeded as the Manager employee (Miguel Santos) specifically
  so the point-adjustment REQUEST flow is testable without an admin login, while
  approve/reject stays hidden.
- When real EF-backed services are ready: swap the right-hand side of each property in
  ServiceRegistry.cs and delete the Mock* classes plus Common/PrivateSetterAccessor.cs
  (a reflection shim only the mocks need).

5. UI DECISIONS — SHELL / CUSTOMERS / FEEDBACK
====================================================================
- Sidebar lives on the RIGHT. Distinct tone (Tint85) from page background (Tint95) and
  white card surfaces, footer a step darker (Tint75).
- A thin top bar spans the full width above the sidebar (brand mark + "Morcaffein" +
  active tab name), 60px tall. Transactions/POS does NOT get a second banner of its own.
- No account-switcher control — the logged-in staff name/role in the sidebar footer is a
  plain read-only Label, not a ComboBox.
- Table headers use Tint50 with dark text; selected-row highlight uses Tint90. Column-
  header click-to-sort doesn't flash the default system blue.
- Disabled buttons visibly grey out (BrandPalette.ButtonDisabledFill/Text via
  Theme/ButtonStyler.cs's TrackEnabledState helper).
- Star ratings (Feedback logging) are hollow (☆) when unfilled, solid brand-colored (★)
  up to the hovered/clicked count.
- Onboarding a new customer is a 2-step modal (Details -> Confirm) with a Back button.
- Log Feedback modal is also 2-step (pick customer via its own search -> rating/category/
  notes), with Cancel only on step 1, replaced by Back on step 2.
- The Feedback ticket drawer's review content is boxed into its own bordered card.
- Order History (Customers drawer) has NO Status column — every row is a completed sale.
- FEEDBACK DRAWER IS NOW REVIEW-ONLY. The decision panel (bonus points / resolution notes
  / Resolve & Award / Dismiss) that used to sit below the review box has been removed.
  Staff log and view; managers decide elsewhere.
- FEEDBACK / CUSTOMERS DRAWER GROUPING: the Feedback drawer boxes its review content;
  the Customers drawer boxes the profile block (name/tier/points/contact) in its own
  bordered card, matching that pattern. The three sub-grids below (Order History, Ledger,
  Adjustment Requests) remain loose header+grid pairs, not individually boxed.

6. TRANSACTIONS/POS — DESIGN
====================================================================
The owner sketched a low-fi wireframe (search bar, customer profile, drink cards with
S/M/L/XL size buttons, an Order box, a Payables box, "Log Sale"). Final layout
(Views/Controls/TransactionView.cs):

- ONE boxed card containing three regions side by side plus nothing outside it — no
  second top banner. Customer info lives inline in the left column.
- LEFT COLUMN (260px): a single search box that looks up ONLY by Customer ID or contact
  number. The matched customer's profile (name, tier, points, contact) appears below the
  search box once found. At the bottom of the column: the promo button (see section 3).
- MIDDLE: "Drinks" header + a "Sort by Category" ComboBox + a drink-name search box, then
  a wrapping FlowLayoutPanel of ProductCardControl cards. Each card shows S/M/L/XL
  quick-add buttons (positional labels by index, not derived from each product's actual
  SizeName text). Tapping one adds that size, qty 1, no modifiers, to the cart. Clicking
  the card body opens FrmItemCustomizer for modifiers / a different quantity.
- RIGHT COLUMN (380px): three bordered boxes stacked:
    * "Order" box (Fill, scrolls) listing CartLineControl rows.
    * "Payables" box (Bottom) with Subtotal / Discount / VAT (12%, display-only) /
      PWD-Senior Disc. (static ₱0.00 placeholder) / Total.
    * "Log Sale" box (Bottom) with a full-width Log Sale button.
  The column has 10px padding so all three boxes are inset uniformly from the card edge.

- CART LINE LAYOUT (Views/Controls/CartLineControl.cs):
    * Row is 44px. Left-to-right: name (fills, ellipsized single-line), price (76px,
      right-aligned ₱SubTotal), stepper cluster (94px: −, 1x, +), 10px gap, ✕ (28px).
    * The name label is height-constrained to a single line so AutoEllipsis fires instead
      of wrapping to two lines.
    * The stepper and ✕ are inside a shared rightCluster panel, with the gap between them
      being real empty space inside that panel — not a Margin between docked siblings
      (WinForms packs those flush and honors margins inconsistently).
    * Children are absolutely positioned in LayoutChildren(), called from OnResize and
      OnHandleCreated. Both children of the FlowLayoutPanel stepper carry
      Margin = new Padding(0) — FlowLayoutPanel's default 3px-per-side margin was
      squeezing the trailing + button out of the 94px stepper.
    * The ✕ is a Label, not a Button — WinForms FlatStyle buttons enforce a minimum width
      larger than 28px, which visually overlapped the +.

- GOTCHA WORTH REMEMBERING: never set Dock on a direct child of a FlowLayoutPanel — the
  panel positions children itself and Dock fights it. This was the original "cart lines
  don't render at all" bug.

- Seeded promos: Birthday Treat (20% off, birthday-only), Gold Member Perk (₱50 off,
  Gold tier + ₱200 min), We Miss You (15% off, inactive customers), and Exam Week
  (10% off, all tiers, no minimum, 50 redemptions) — the last one exists specifically so
  "Select a Promo" is never empty in ad-hoc testing.

7. PENDING / KNOWN GAPS
====================================================================
- Real login (FrmLogin) is deferred — not a bug, just not in scope yet.
- A future admin console (or an admin-capable login) is the natural home for:
    * The approve/reject side of the point-adjustment workflow.
    * The resolve/dismiss/award-bonus side of feedback handling (removed from this app
      this session — see section 3).
- VAT/PWD-Senior discount on the POS are cosmetic placeholders. Turning them into real,
  functioning discount logic is unassigned future work.
- Order.ApplyPromo has no duplicate guard at the domain level; the UI blocks re-selecting
  the same promo on one order, but the domain permits it. A domain-level guard is the
  proper fix and is deferred to the DB-connection workstream.
- The wireframe's sidebar sketch showed a standalone "Registration" nav item separate from
  Transactions/Customers/Feedback; this was NOT added.
- MENU REVISION (deferred, owner's next plan): the product catalog should become
  beverages only (hot & cold), with a base pricing scheme of Regular ₱30 / Large ₱40 /
  XL ₱50 and the modifiers ("additionals") adjusted to match. This is a content/data
  change to MockDataStore.SeedProducts / SeedModifiers and possibly the ProductCategory
  naming ("Espresso"/"Cold Brew" → "Hot"/"Cold"). Not scoped yet — waiting on the owner
  to detail it.
- SwitchCustomer (relink-the-existing-order) on TransactionViewModel is now unused by the
  POS flow — search-and-Go starts a fresh VM/Order instead. Left in place since the Quick
  Register relink flow may want it later; harmless if never called.
