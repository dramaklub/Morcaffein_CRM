MORCAFFEIN CRM — PROJECT PLAN & BUSINESS CONTEXT
(Companion to ai-context-bundle.txt, which has the actual code. This file explains the
WHY behind it — the goal, the decisions made along the way, and what's left.)

====================================================================
1. WHAT THIS PROJECT IS
====================================================================
A Coffee Shop Loyalty & Retention CRM ("Morcaffein") — a WinForms desktop app (.NET,
net10.0-windows) for the STAFF side of the business, backed by a real EF Core + SQL
Server database accessed through a web API. Not a mock anymore — every feature reads
and writes the real tenant DB.

The Staff UI has three pillars — ALL THREE ARE NOW FULLY API-BACKED:
  1. Transactions / POS — recording sales, promos, PWD/Senior discount
  2. Customer management — search/register/history/point adjustments
  3. Feedback — logging + viewing tickets

Login/auth is still OUT OF SCOPE for now — FrmLogin exists as a stub, Program.cs
launches straight into FrmMain, and a placeholder employee session is seeded in code.
Login is the NEXT major piece of work (see section 8).

====================================================================
2. ARCHITECTURE / STACK DECISIONS
====================================================================
- WinForms, not WPF.
- MVC (not MVVM). Controllers are plain classes:
    - WinForms side: Controllers/*.cs — UI controllers that read inputs, call the API,
      update controls. No bindable properties, no commands.
    - API side: CRM_Morcaffein.api/Controllers/*.cs — [ApiController] classes that
      contain all business rules and persistence.
  Common/ObservableObject.cs and Common/RelayCommand.cs were deleted long ago; the
  ViewModels/ folder is empty.

- DDD-lite domain entities in CRM_Morcaffein.domain/entities. Mostly public-set
  properties now (the earlier "mutate only via domain methods" pattern was relaxed
  when the entities became primarily a data shape used across the API boundary).
  Business rules moved to the API controllers.

- EF Core 10 with TWO contexts:
    - MasterCrmDbContext (multitenant: Companies, CompanyDatabases, Devices)
    - TenantCrmDbContext (per-tenant: Customers, Orders, Products, etc.)

- Multitenant setup:
    - Master DB (db66493.public.databaseasp.net) maps CompanyId → tenant DB info.
    - Each tenant has its own database on MonsterASP.
    - Currently three tenants exist (Tenant A/B/C), but the app hardcodes tenant A
      (companyId = 1 → db67068) via ApiConfig.CompanyId on the client.

- Architecture: WinForms → HTTP → CRM_Morcaffein.api → EF Core → SQL Server.
  The API is the single source of truth — it holds the connection strings, resolves
  tenants, validates input, and recomputes totals. The WinForms app has no direct
  DB access.

- Design-time factory for migrations: TenantCrmDbContextFactory in
  infrastructure/data/ implements IDesignTimeDbContextFactory<TenantCrmDbContext>.
  The connection string is HARDCODED in this file because it only runs during
  `dotnet ef` commands — never at runtime. Update both this file and appsettings.json
  if the tenant DB moves.

3. KEY BUSINESS RULES
====================================================================
- POINT ADJUSTMENTS — manager/admin approve/reject:
    * Anyone (Barista included) can REQUEST a point adjustment.
    * Only Admin/SuperAdmin can APPROVE or REJECT.
    * An employee can NEVER approve their own request.
    * Approved requests write a PointLedger row (Type="Adjustment") and update
      Customer.PointsBalance atomically.
    * Rejected requests do not touch the balance.

- FEEDBACK — log + view only in the staff app:
    * Any staff member can log a feedback ticket against a customer.
    * Resolving/dismissing is a manager decision on a future manager/admin surface.
    * Staff-side flow: log a ticket → see it in the grid → click for details.

- TRANSACTIONS/POS:
    * ALWAYS requires a real customer (no walk-in/guest path).
    * Search-and-Go starts a fresh transaction, with confirmation if a cart has items.

- PROMOS:
    * Applied via a single button in the left column. Only ONE promo per order.
    * Discount computed on the SubTotal, capped by MinPurchaseAmount and
      MaxDiscountAmount.
    * **PROMO DISCOUNT CAP** — see section 7, needs to be reviewed/wired.

- PWD/SENIOR DISCOUNT (stacked, standard PH method):
    * Toggled via a checkbox in the Payables panel.
    * STACKS on top of any promo discount.
    * Computed as: `NetOfVat = AfterPromo / 1.12; PwdDiscount = NetOfVat * 0.20`.
    * Stored on Order as HasPwdSeniorDiscount (bool) + PwdSeniorDiscountAmount (decimal).
    * Recomputed SERVER-SIDE on checkout; the client's numbers are never trusted.
    * Points earned = (int)(FinalTotal / 10), on the post-discount amount.

- VAT line in the Payables panel is DISPLAY-ONLY (assumes VAT-inclusive pricing, PH
  receipt style). It's computed as `(SubTotal - PromoDiscount) / 1.12 * 0.12`.

- Tiers (Regular/Silver/Gold) are plain text with no color-coding.

5. UI DECISIONS
====================================================================
- Sidebar on the RIGHT. Top bar 60px with brand mark + active tab name.
- No account switcher.
- Table headers use Tint50 with dark text; selected rows use Tint90.
- Disabled buttons grey out via ButtonStyler.TrackEnabledState.
- Customers + Feedback tabs: searchable grid + left drawer. Rows do NOT auto-select
  on load (was intentionally removed — single-row grids felt unclickable when they
  auto-selected).
- Customers drawer: profile block in its own bordered card, order history / ledger /
  adjustment requests below.
- Feedback drawer: review content boxed into a card.
- New Customer: 2-step modal (Details → Confirm).
- Log Feedback: 2-step modal (pick customer → rating/category/notes).
- FrmItemCustomizer: grew to 400×720 to fit 21 modifiers, with a fixed-height
  (320px) scrollable modifier panel so long add-on lists don't overflow.

====================================================================
6. TRANSACTIONS/POS
====================================================================
- One boxed card with three columns: customer + promo (left, 260px), drinks (middle,
  fills), order + payables + log sale (right, 380px).
- Cart is CLIENT-SIDE: in-progress Order built and mutated in TransactionController
  in memory. Only CompleteSaleAsync hits the API.
- The server RE-COMPUTES all totals and PWD/Senior from raw IDs at checkout.
- Product catalog is cached per app session via ProductCatalogCache (single
  "full-catalog" endpoint). This was the biggest speed win.
- Tenant database resolver and DbContextOptions are cached process-wide (static
  ConcurrentDictionary) so subsequent API calls don't re-hit the master DB.

7. PENDING / KNOWN GAPS
====================================================================
- LOGIN — see section 8 for the plan.
- Manager / Admin / SuperAdmin additions — see section 8.
- **Promo discount cap** — MaxDiscountAmount is stored on Campaign and respected by
  CalculateDiscount on both sides, but there's no explicit test coverage yet. The
  runtime behavior works, but there's no admin surface to set the cap. Needs to be

8. ACTIVE NEXT PLANS
====================================================================
1. REAL LOGIN
   - Build POST /auth/login on the API. Accepts username + password.
   - Reads Credential from tenant DB, verifies (currently plaintext; BCrypt later),
     returns a JWT with claims: EmployeeId, CompanyId, Role.
   - Wire FrmLogin properly, replace PlaceholderStaffAccount with a real session.
   - Update ApiConfig to send Authorization: Bearer <token> on every request.
   - Token lifetime: 8-12 hours (shift-length). No refresh tokens.
   - The API needs auth middleware to validate the token and populate
     HttpContext.User with the claims.

2. MANAGER / ADMIN / SUPERADMIN ADDITIONS
   - Role checks currently in the client only (e.g. CanApprove = IsAdmin(Role)).
     The API needs to enforce these server-side via JWT role claims.
   - The approve/reject UI for point adjustments needs to be reachable: right now
     the placeholder session is a Barista so the approve/reject panel is hidden.
     Once login is real and a Manager/Admin logs in, the panel appears.
   - The role hierarchy: Barista < Manager < Admin < SuperAdmin. Baristas can
     REQUEST point adjustments; Managers can REQUEST but not approve; Admins and
     SuperAdmins can approve/reject.
   - Feedback resolution (currently removed from this app) belongs on an admin
     surface. When that's built, the API gets Resolve/Dismiss endpoints and the
     Feedback entity already has DecidedBy / DecidedAt / DecisionNotes columns.

3. PROMO DISCOUNT CAP REVIEW
   - MaxDiscountAmount exists on Campaign and is respected by both the client's
     preview math and the server's recompute.
   - No admin UI to set it — campaigns are seeded via SQL for now.
   - When the admin console is built, needs a form field for the cap.
   - Until then, any existing campaigns with a cap should be verified in SSMS.
