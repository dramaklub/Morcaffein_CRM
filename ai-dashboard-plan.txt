MORCAFFEIN CRM — DASHBOARD FEATURE PLAN & CONTEXT
Written 2026-09-20. This is a standing reference for whoever (human or AI) builds the
remaining dashboard charts — it exists so every chart added after this point follows
the same pattern instead of each one reinventing the plumbing. Update this file
whenever a new chart ships or a scope decision changes.

=====================================================================
1. SCOPE (as given by the user, verbatim intent preserved)
=====================================================================

  SHARED (Manager + Admin both see these — same chart, same data):

2. ARCHITECTURE DECISION: charting library
=====================================================================

Chosen: WinForms.DataVisualization (NuGet package — the actively maintained .NET
5+/8+ port of the classic MSChart control; note the package ID is
"WinForms.DataVisualization", NOT "System.Windows.Forms.DataVisualization" — that
name has no stable release and only resolves a 2020 prerelease). Decided over
hand-rolled GDI+ (the style ProductCardControl/CampaignCardControl use)
specifically because the heatmap and dual-axis combo chart are real charting math
that's easy to get subtly wrong by hand; a maintained charting engine handles axis
scaling, dual Y-axes, and color-mapped cells correctly out of the box.

Already added to CRM_Morcaffein.winforms.csproj:
    <PackageReference Include="WinForms.DataVisualization" Version="1.10.2" />
Confirmed compatible with net10.0-windows and builds clean (0 warnings/errors).

Namespace: System.Windows.Forms.DataVisualization.Charting — the control class is
`Chart`, series are `Series` with `ChartType` (Column, StackedColumn, Line, Pie/
Doughnut, Point, etc.), axes are `ChartArea.AxisX`/`AxisY` (a second Y axis for
dual-axis combo charts is a second ChartArea or a Series with `YAxisType =
AxisType.Secondary`).

Heatmap approach: there is no native "Heatmap" SeriesChartType. The established
pattern for a heatmap in this control is a bubble-less "Point" series per (hour,
day) cell with `MarkerStyle = Square` sized to fill the cell, colored via a
computed gradient (light-to-brand-color) based on the cell's value relative to the
dataset's max — OR forgo the Chart control for this one chart specifically and
render it as a self-painted grid (matching ProductCardControl's OnPaint
convention), which is arguably simpler and more precise for a strict grid layout
than coercing the Chart control into one. This session's implementation uses the
self-painted-grid approach for the heatmap specifically (see PeakHoursHeatmapControl
below) — reconsider only if a later chart also needs true bubble/scatter
behavior, in which case standardizing on the Chart control's Point-series method
might be worth revisiting for consistency.

3. ARCHITECTURE DECISION: layered pattern (mirrors the Campaign feature exactly)
=====================================================================

Every chart follows this same four-layer shape — this IS the model other AI
sessions should copy:

  a) API DTO(s) — CRM_Morcaffein.api/DTOs/DashboardResponseDtos.cs (one file,
     grouped by chart, to avoid a DTO-file explosion for what will eventually be
     10 charts). Each chart gets its own small DTO shaped exactly as its chart
     needs (pre-aggregated — the API does the GROUP BY, not the client).

  b) API Controller — CRM_Morcaffein.api/Controllers/DashboardController.cs (new).
     Route: api/tenant/{companyId:int}/dashboard/... One GET endpoint per chart
     (e.g. GET .../dashboard/loyalty-tier-progression, GET .../dashboard/peak-hours).
     [Authorize] like every other controller. No role check inside individual
     endpoints for the SHARED charts (both Manager and Admin can call them); the
     six Manager-only/Admin-only charts, once specced, DO need a role check
     mirroring CampaignController's `creator.Role.Equals("Manager", ...)` pattern.

  c) WinForms API client — CRM_Morcaffein/Services/Api/DashboardApi.cs (new).
     Same shape as CampaignApi.cs: one HttpClient from ApiClientFactory.Create(),
     one method per endpoint, EnsureSuccess-style error parsing (reuse the
     existing pattern — every *Api.cs file in Services/Api/ repeats it verbatim,
     don't invent a new one).

  d) WinForms Controller — CRM_Morcaffein/Controllers/DashboardController.cs (new).
     Thin wrapper, same shape as the existing WinForms CampaignController/
     CustomerController — forwards to DashboardApi, no business logic (matches
     the "all business rules live on the API side" doc-comment convention already
     established in every other WinForms controller this session).

  e) WinForms View — CRM_Morcaffein/Views/Controls/ManagerDashboardView.cs (new,
     replaces the Manager's PlaceholderView) and, later,
     AdminDashboardView.cs (replaces the Admin's PlaceholderView). Each dashboard
     view is a scrollable card grid (same AutoScroll-wrapper-plus-TableLayoutPanel
     pattern TransactionView/CampaignManagementView already use) hosting one small
     UserControl per chart. Each chart gets ITS OWN UserControl file (e.g.
     LoyaltyTierProgressionControl.cs, PeakHoursHeatmapControl.cs) rather than
     inlining chart-building code into the dashboard view — keeps each chart
     independently testable/replaceable and matches the "one control per visual
     unit" convention (ProductCardControl, CampaignCardControl, ApprovalCardControl
     are all precedent for this).

Wiring: in FrmMain.cs, BOTH `navItems.Add(("Dashboard", ...))` lines (Admin at
line ~88, Manager at ~96) currently instantiate `PlaceholderView`. Manager's line
changes to `new ManagerDashboardView()`. Admin's stays PlaceholderView until the
Admin-only charts (8-10) are specced — don't build AdminDashboardView prematurely
with only the 3 shared charts in it; ask whether a partial Admin dashboard (shared
charts only, admin-only charts added later) is wanted, or whether to wait for the
full Admin scope first.

4. DATA AVAILABILITY — verified against the actual schema, not assumed
=====================================================================

All 5 shared charts are computable from what already exists. Checked directly
(CRM_Morcaffein.domain/entities/*.cs) rather than assumed:

  - Chart 1 (Age/AOV): Customer.Birthday (nullable — customers without a
    recorded birthday can't be bucketed; decide whether to exclude them or bucket
    as "Unknown" when building this) + Order.TotalAmount joined by CustomerId.
  - Chart 2 (Campaign lift): Order.OrderDate/TotalAmount + CampaignRedeem.RedeemDate
    (CampaignRedeem entity, confirmed has RedeemDate, CampaignId, DiscountUsed,
    OrderId via Order nav) — group both by date within the campaign's
    StartDate/EndDate window.
  - Chart 3 (Feedback): Feedback.Rating (1-5) + Feedback.DateLogged, joined to
    Customer for age bracket or live tier (via CustomerController.GetTier —
    reuse that exact static method rather than re-deriving the thresholds
    somewhere else, matching the "one home per business concept" rule already
    established this session).
  - Chart 4 (Peak hours): Order.OrderDate — extract Hour and DayOfWeek client-
    side of the SQL grouping (EF can group by both directly).
  - Chart 5 (Loyalty tier progression) — the one real gap: there is no stored
    historical tier snapshot. Customer.PointsBalance is a live current value
    only. Reconstructing "how many customers were Gold as of end of March" needs
    a running-total query over PointLedger: for each month boundary, sum each
    customer's PointLedger.PointsChange where Timestamp <= that boundary, then
    bucket the running total through CustomerController.GetTier's thresholds.
    This is a real, computable SQL/LINQ query (window function or per-customer
    grouped sum), just meaningfully more complex than the other four — budget
    more implementation time for this endpoint specifically.
